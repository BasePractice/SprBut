# Часть 30 — события пользователям по SSE

[← к списку модулей](../README.md) · [модуль 21 «WebFlux»](../21-webflux/README.md)

## О чём эта часть

Модуль 21 показывает `Flux`, которому есть куда течь: подписчик рядом,
в том же процессе. Server-Sent Events выносят подписчика в браузер и держат
соединение открытым часами. Пока экземпляр сервиса один, этого достаточно.
Как только экземпляров два, событие для пользователя может прийти не туда,
где открыт его поток. Эта часть — про то, как доставить событие
пользователю, не зная, к какому экземпляру он подключён.

## Как устроено

Отправка не доставляет событие сама, а публикует уведомление в общий канал
Redis pub/sub. Каждый экземпляр подписан на канал и раздаёт пришедшее своим
подключённым пользователям; у кого пользователя нет, тот уведомление
просто пропускает.

У каждого пользователя на экземпляре одна «толпа» — общий источник событий
и число открытых потоков: вкладок, устройств. Толпа появляется с первым
потоком и исчезает с последним, и вход и выход меняют карту только атомарно.
Иначе последний уходящий мог бы выбросить источник, на который как раз
подписывается новый.

## Примеры

| Класс | Что показывает |
|---|---|
| [`SseEndpoint`](src/main/java/ru/sprbut/m30/SseEndpoint.java) | Поток `text/event-stream` с пингами, чтобы прокси не закрыл молчащее соединение |
| [`SinkAudience`](src/main/java/ru/sprbut/m30/SinkAudience.java) | Пользователи экземпляра: толпы в `ConcurrentMap`, вход и выход через `compute` |
| [`Crowd`](src/main/java/ru/sprbut/m30/Crowd.java) | Неизменяемая толпа: `Sinks.many().multicast()` и счётчик подписчиков |
| [`RedisBus`](src/main/java/ru/sprbut/m30/RedisBus.java) | Общий канал на `ReactiveStringRedisTemplate` |
| [`Relay`](src/main/java/ru/sprbut/m30/Relay.java) | `SmartLifecycle`: подписка на канал живёт вместе с контекстом, битое уведомление пропускается, обрыв лечится переподпиской с паузой |
| [`ParsedNotice`](src/main/java/ru/sprbut/m30/ParsedNotice.java) | Уведомление из канала разбирается только при доставке, поэтому ошибка разбора не рвёт подписку |
| [`MeteredAudience`](src/main/java/ru/sprbut/m30/MeteredAudience.java), [`MeteredBus`](src/main/java/ru/sprbut/m30/MeteredBus.java) | Метрики декораторами: открытые потоки, отправленные и полученные уведомления |

## API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/sse/stream/{user-id}` | Поток событий пользователя (`text/event-stream`) |
| POST | `/sse/send/user/{user-id}` (`text/plain`) | Событие `user-event` одному пользователю на всех экземплярах |
| POST | `/sse/send/broadcast` (`text/plain`) | Событие `broadcast` всем подключённым |
| GET | `/actuator/prometheus` | Метрики `sse_server_*` и `redis_sse_*` |

Поток не проверяет, чей он: идентификатор пользователя берётся из пути.
В настоящей системе его приносит gateway, как в [части 29](../29-spring-cloud/README.md).

## Ключевые выводы

* Горизонтальное масштабирование ломает простую модель «отправил — доставил»:
  отправитель не знает, где получатель. Общий канал превращает адресную
  доставку в рассылку всем экземплярам с фильтром на месте.
* Redis pub/sub ничего не хранит: экземпляр, отключённый от канала в момент
  публикации, уведомление не получит никогда. Для событий, которые нельзя
  терять, нужен журнал — Redis Streams или брокер.
* Подписка на канал — ресурс приложения, а не запроса. Её место
  в жизненном цикле контекста, а не в методе контроллера.
* Медленный клиент не должен тормозить остальных: источник
  `directBestEffort` отдаёт событие тем, кто готов его принять,
  и не ждёт отстающих.

## Запуск

```bash
mvn -pl 30-spring-sse test
```

Два экземпляра за общим Redis поднимаются в Docker:

```bash
mvn -pl 30-spring-sse -DskipTests package
docker compose -f 30-spring-sse/docker-compose.yaml up -d --build
```

Сквозной сценарий — [`http/sse.http`](http/sse.http), окружение `docker`
в IntelliJ HTTP Client: уведомления отправляются через второй экземпляр,
а приём проверяется по метрикам первого. Без IDE, из каталога модуля:

```bash
docker run --rm --network 30-spring-sse_default -v "$PWD/http":/workdir jetbrains/intellij-http-client --env-file http-client.env.json --env docker -V one=http://sse-one:8080 -V two=http://sse-two:8080 sse.http
```
