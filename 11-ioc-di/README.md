## Что в презентации

> Инверсия управления (IoC). Внедрение зависимостей. IoC-контейнер отвечает
> за создание объектов и управление их жизненным циклом. Фабрика — обеспечивает
> создание экземпляров объектов. DI использует IoC и фабрики.
> Пример без зависимостей → пример ручное управление → пример управление DI Spring.

Три «примера» со слайда — это три шага одного пути, и модуль повторяет их буквально.

## Шаг в сторону: Dagger

Spring — не единственный способ сделать DI, и даже не единственный способ сделать
контейнер. [Dagger](src/main/java/ru/sprbut/m11/step4/WiringModule.java) собирает
ровно тот же граф, но не в рантайме: `@Component` — это задание процессору
аннотаций (модули 07–09), а результат — обычный Java-код в
`target/generated-sources`, который можно открыть и прочитать.

| | Spring | Dagger |
|---|---|---|
| Когда собирается граф | при старте контекста | при компиляции |
| Чем собирается | рефлексия и прокси | сгенерированный код |
| Когда видно забытую зависимость | при старте приложения | при компиляции |
| Профили, условные бины, `@Value` | есть | нет |
| Цена старта | пропорциональна числу бинов | нулевая |

Отсюда и области применения: Dagger родом из Android, где рефлексия дорога,
а старт должен быть мгновенным; Spring живёт на сервере, где важнее гибкость
конфигурации. Обмен один и тот же во всей инженерии — гибкость против ранней
проверки.

## Шаг в сторону: пул объектов

Контейнер решает две задачи: подобрать зависимости и распорядиться временем жизни.
[`ObjectPool`](src/main/java/ru/sprbut/m11/pool/ObjectPool.java) — вторая задача
без первой. Клиент не пишет `new` и не решает, когда объекту умереть: он просит
объект и возвращает его обратно, а пул решает, создать новый или отдать
отложенный.

| | Фабрика | Пул | Контейнер |
|---|---|---|---|
| Подбирает зависимости | нет | нет | да |
| Управляет временем жизни | нет | да | да |
| Кто зовёт `new` | фабрика | фабрика по просьбе пула | контейнер |

Возвращать объект руками — то же самое, что звать `free`: забыли — пул стал
генератором мусора, позвали дважды — один объект достался двум владельцам.
Поэтому у пула есть второй вход, где за возврат отвечает язык:

```java
try (ObjectPool.Lease<StringBuilder> lease = pool.lease()) {
    lease.object().append("работа");
}
```

Отсюда видно, откуда в Spring `singleton` и `prototype`: это и есть два ответа
на вопрос «создавать заново или отдать существующий», а пул — третий, между ними.
Так же устроены пулы соединений, которые Boot настраивает за нас в `DataSource`.

Пул изменяем — и это единственное место модуля, где правило неизменяемости
из [RULE.md](../RULE.md) отступает намеренно: хранимое между вызовами состояние
здесь и есть предмет разговора.

## Расширенный пример

[`MiniContainer`](src/main/java/ru/sprbut/m11/extended/MiniContainer.java) — работающий
IoC-контейнер примерно на 150 строк: сканирует классы с
[`@MiniComponent`](src/main/java/ru/sprbut/m11/extended/MiniComponent.java), разбирает
конструкторы рефлексией, рекурсивно создаёт зависимости и кэширует синглтоны.

Он умеет и падать так же, как настоящий: на неоднозначности, на отсутствующем бине
и на циклической зависимости. После того как контейнер написан руками, сообщения
Spring перестают быть загадочными — становится видно, из какого именно места
проверки они приходят.

## Ключевые выводы

* IoC — это про то, **кто принимает решение**. `new` внутри класса означает, что
  решение принимает сам класс, и подменить его нельзя ничем, кроме правки кода.
* Фабрика — половина контейнера: она умеет создавать, но не умеет разрешать граф.
* Контейнер добавляет к фабрике ровно две вещи: подбор аргументов по типу
  и управление временем жизни.
* DI работает и без Spring. Конструктор, принимающий интерфейс, — это уже DI.
* Рантайм контейнеру тоже не обязателен: Dagger разрешает граф компилятором,
  и в приложение попадает сгенерированный код, а не рефлексия.
